# Rekindle PRD（產品需求文件）

狀態：草稿 v0.2 ｜ 2026-10-10 ｜ 技術設計見 [TDD.md](TDD.md)

## 1. 這是什麼

Rekindle 是一個公開的 Spark on Kubernetes 故障分診與自動復原平台。Spark job 失敗後，它會收集 K8s 事件、driver/executor log、Spark event log 三層訊號，先比對過往案例：見過的故障直接套用驗證過的修法，沒見過的才交給 agent 調查。最後改設定重送、驗證結果，並把結論寫回案例庫。

## 2. 為什麼做

要解決的問題：

- Spark job 在 K8s 上失敗時，線索分散在三層，人工查一次很花時間。
- 故障高度重複（OOMKilled、資料傾斜、spot 節點被回收），但每次都被當成新問題重新調查。

專案本身的目的：

- 補上我缺的 Spark 與 K8s 實戰經驗，並接上我熟的 agent 系統。
- 在 2027 年春季投履歷前，有一個真的上線、有評測數字的作品。

## 3. 目標與非目標

目標：

- **G1 看得懂**：訪客不用登入，兩分鐘內看完「失敗 → 診斷 → 修復 → 驗證」的完整循環。
- **G2 有數字**：用評測集量出分診準確率、案例庫命中率與誤命中率，以及有無案例庫時的修復時間與 token 成本。
- **G3 有實用入口**：工程師上傳自己的 event log，就能拿到瓶頸分析與調整建議。
- **G4 我真的學會**：每一種故障我都能親手重現，並解釋它為什麼壞、為什麼這樣修。
- **G5 養得起**：每月營運成本在預算內。

非目標：

- 不改寫使用者的程式碼。第一版的修法只限白名單內的 Spark 設定。
- 不執行訪客上傳的任何程式碼。上傳入口只做分析。
- 不是通用的 Spark 平台：沒有多租戶，沒有 SLA，只支援透過 Spark Operator 跑在 K8s 上的 job。
- 自然語言跑 Spark 不在第一版。
- 不重現任何前雇主內部系統的設計細節或名稱，只用公開概念重新設計。

## 4. 使用者

| 使用者 | 想要什麼 | 對應功能 |
|---|---|---|
| 面試官、招募方 | 很快判斷這個人懂不懂 Spark、K8s 和 agent。注意力大約兩分鐘 | 故障實驗室、評測數字頁 |
| 跑 Spark 的資料工程師 | job 變慢或掛掉，想知道原因和該調什麼 | 上傳 event log 診斷 |
| 我自己（維運兼學習） | 可重現的故障、評測集、成本看得見 | 故障定義檔、評測腳本、成本紀錄 |

## 5. 使用情境與功能需求

### 5.1 故障實驗室（P0）

訪客選一個預先做好的故障，看 agent 的診斷與修復過程，以及修復前後的耗時與成本。

- **L1**：提供 6 種故障，每種都有說明頁，寫明怎麼壞的、標準答案和修法。
- **L2**：預設播放錄製好的真實執行。即時執行另外開放，但有每日配額。原因是 spot 節點從零擴起來要幾分鐘，而且每次執行都要付錢。
- **L3**：過程以時間軸呈現，每個結論都標出證據來自哪一層訊號、哪一段內容。
- **L4**：同一種故障並排顯示「第一次遇到（未命中）」和「再次遇到（命中）」的時間與 token 成本。
- **L5**：公開一頁評測數字，內容對應第 7 節的指標。

### 5.2 上傳 event log 診斷（P1）

- **U1**：上傳單一 event log 檔（可壓縮），有大小上限。
- **U2**：只分析、不執行。這條路徑沒有重送 job 的能力。
- **U3**：檔案進來先遮蔽敏感內容，之後才儲存或送進 LLM。
- **U4**：報告包含瓶頸位置（stage、task 層級）、歸因分類、設定調整建議與依據。
- **U5**：頁面寫明保存期限。原始檔分析完就刪除；只有使用者勾選同意時，去識別化的指紋與分類才寫入案例庫。
- **U6**：不需登入，依 IP 限流。

### 5.3 自然語言跑 Spark（P2，可選）

用中文提問，agent 寫唯讀的 Spark SQL，在限定的公開資料集上執行，有配額。它是「另一種 job 來源」，失敗時走同一個分診循環。

### 5.4 核心循環（三個情境共用）

- **C1 收集**：job 失敗、逾時或明顯慢於基準時，自動收集三層訊號，存成一個案件。
- **C2 指紋**：去掉 ID、時間、路徑後產生錯誤簽章，用來比對案例庫。
- **C3 重用**：命中就套用已驗證的修法；未命中才啟動調查。
- **C4 歸因**：調查的輸出是固定分類表中的一個類別，附證據與信心。
- **C5 修法受限**：修法只能是白名單內的設定，每個設定有上下限。
- **C6 復原與驗證**：重送次數有上限；通過驗證的修法才會以「已驗證」寫回案例庫。
- **C7 降級**：套用後驗證失敗的案例會被降級，不再自動套用。
- **C8 知道何時停手**：設定修不了的故障，明確回報「需要人處理」，不硬修。

## 6. 限制

- **時間**：每週 5–10 小時。
- **預算**：伺服器每月 US$50–150；LLM 費用另計，設每日上限。
- **保密**：文章與文件只寫「受過往經驗啟發」，不描述前雇主內部系統。
- **隱私**：event log 可能含 SQL 內容、路徑，甚至設定裡的金鑰。
- **安全**：agent 只有最小權限。log 是不可信的輸入，不能讓 log 內容影響 agent 能做的事。

## 7. 成功指標

這一節只定義要量什麼。目標值還沒定，等階段 2 跑出 baseline 再討論。

| 指標 | 定義 |
|---|---|
| 分診準確率 | 未命中路徑中，歸因類別與標準答案一致的比例 |
| 案例庫命中率 | 重複出現的故障中，直接命中的比例 |
| 誤命中率 | 命中的案件中，套到錯誤案例的比例 |
| 復原成功率 | 重送後成功且通過驗證的比例 |
| 修復時間 | 從偵測到失敗，到驗證通過；分命中與未命中 |
| token 成本 | 每個案件的 LLM 用量；分命中與未命中 |
| 月營運成本 | GCP 加 LLM |
| 展示時間 | 訪客看完一個完整案例所需時間 |

## 8. 里程碑

| 階段 | 週 | 預計完成 | 產出 | 完成定義 |
|---|---|---|---|---|
| 0. 打底 | 1–3 | 2026 年 10 月底 | 本機 kind + Spark Operator 跑通 TPC-DS | 一行指令能重建環境並跑完一個查詢；能在 History Server 上說明一個 stage 的時間花在哪 |
| 1. 故障實驗室 | 4–8 | 2026 年 12 月初 | GKE 叢集、6 種故障 | 每種故障都能穩定重現，附標準答案、手動修法、修復前後的數字 |
| 2. 分診循環 | 9–14 | 2027 年 1 月中 | 收集、指紋、案例庫、調查 agent、評測腳本 | 在評測集上跑出第 7 節所有指標的 baseline |
| 3. 復原與上線 | 15–18 | 2027 年 2 月中 | 自動重送與驗證、公開網站 | 訪客不用登入就能看完一個完整案例；月成本在預算內 |
| 4. 上傳診斷 | 19–24 | 2027 年 3 月底 | event log 上傳入口 | 遮蔽規則有測試；從上傳到拿到報告不需人工介入 |
| 5. 自然語言 | 之後 | 未排 | 唯讀 SQL 入口 | 不排時程 |

階段 3 上線是唯一的硬目標。階段 4、5 可以延後。

## 9. 風險

| 風險 | 對策 |
|---|---|
| 時間都花在熟悉的 agent 上，Spark 和 K8s 沒學到 | 階段 0–1 不寫 agent，先親手做出每一種故障 |
| 評測集太小，數字沒有說服力 | 每種故障做多個變體，並加入健康的 job 與分類表以外的故障當對照 |
| 案例庫誤命中，套了錯的修法 | 驗證失敗就退回調查並降級該案例；誤命中率列為正式指標 |
| 成本失控 | spot 節點縮到零、namespace 資源配額、即時執行配額、LLM 每日上限、GCP 預算警示 |
| 即時展示不穩（spot 沒容量、節點擴太慢） | 預設播放錄製的執行 |
| 範圍膨脹 | 自然語言入口不排時程；兩個 agent 框架中，agno 的部分最先砍 |
